시스템 설계 예상문제 · 중급 정답

중급 시스템 설계 문제에 대한 하나의 답변 예시입니다. 정답을 암기하기보다 가정, 판단 근거, 대안과 실제 경험을 자신의 언어로 설명하는 데 활용하세요.

답변 활용 안내 · 아래 답변은 유일한 정답이 아닙니다. 현재 규모와 제약에서 선택한 이유를 확인하고, 실제 면접에서는 본인이 경험한 문제·행동·결과를 덧붙여 답변하세요.

한정 수량 공동구매 서비스

상황

커머스 서비스 ‘DealBox’가 매주 금요일 한정 수량 공동구매를 엽니다. 평소에는 초당 300건 정도지만 인기 상품이 공개되면 10분 동안 초당 2만 건의 조회와 주문 요청이 몰립니다. 지난 행사에서는 상품 페이지가 느려지고, 같은 상품이 재고보다 37개 더 판매되었습니다.[요청] “사용자가 페이지를 빠르게 보고 주문할 수 있어야 하지만, 재고보다 많이 판매해서는 안 됩니다. 결제 실패로 확보된 재고가 계속 묶이는 문제도 해결해 주세요.”

조건

규모와 시스템 구성

  • 회원 500만 명, 행사 동시 접속 20만 명
  • 상품별 수량 1천~1만 개
  • Spring Boot, MySQL, Redis 구성

현재 문제와 제약

  • Traffic행사 시작 시 조회·주문 집중
  • Stock동시 주문으로 초과 판매
  • Timeout결제 실패 후 재고 미반환

꼬리 질문

1

조회 요청과 주문 요청을 구분해 어디부터 확장하겠습니까? 캐시, 서버 증설, DB 튜닝의 우선순위와 그 이유를 설명해 주세요.

답변 예시 보기

진단과 접근

조회와 주문은 병목의 성격이 다릅니다. 상품 설명처럼 자주 바뀌지 않는 조회는 캐시와 CDN으로 흡수하고, 주문은 재고 정합성을 지켜야 하므로 처리량을 제한하며 DB까지 도달하는 요청 수를 관리하는 것이 먼저입니다.

설계와 운영

  • 상품 상세·이미지는 CDN과 Redis에 캐시하고 TTL에 지터를 주어 행사 시작 시 동시 만료를 줄입니다.
  • 주문 API는 별도 서버 풀과 커넥션 풀을 사용하고 대기열 또는 rate limit으로 DB 처리량 이상의 요청을 받지 않습니다.
  • 캐시 적중률, DB 커넥션 사용률, 주문 p95, 오류율을 함께 보고 병목이 실제로 이동했는지 확인합니다.

서버만 늘리면 조회 처리량은 늘어도 하나의 재고 행에 대한 경쟁은 해결되지 않습니다. 먼저 부하 테스트로 조회와 주문의 최대 처리량을 따로 측정하고, 가장 먼저 포화되는 자원부터 개선하는 순서가 안전합니다.

경험 연결 포인트 · 트래픽 급증 시 캐시·서버·DB 중 어디가 먼저 포화됐는지 관측하고 개선한 경험을 수치와 함께 설명합니다.
2

여러 사용자가 마지막 한 개를 동시에 주문할 때 초과 판매를 막는 방법을 제시해 주세요. DB 조건부 갱신과 Redis 재고 관리 중 무엇을 선택할지도 설명해 주세요.

답변 예시 보기

진단과 접근

핵심 불변식은 성공한 주문 수가 재고를 넘지 않는 것입니다. DB를 기준 원장으로 사용한다면 재고 조회와 차감을 분리하지 말고 조건부 갱신 한 번으로 처리해 경쟁 조건을 막을 수 있습니다.

설계와 운영

  • 예를 들어 UPDATE 상품 SET stock=stock-1 WHERE id=? AND stock>0의 영향 행 수가 1일 때만 예약을 성공시킵니다.
  • Redis를 사용한다면 Lua로 확인과 차감을 원자적으로 처리하고, reservationId와 멱등키를 함께 기록합니다.
  • DB unique constraint와 주문별 idempotency key를 마지막 안전장치로 두어 재시도가 두 번 차감하지 않게 합니다.

DB 조건부 갱신은 단순하고 신뢰하기 쉽지만 인기 상품 한 행에 쓰기가 집중됩니다. Redis는 처리량이 높지만 DB 반영·장애 복구가 추가되므로 현재 규모와 팀 운영 역량을 근거로 선택합니다.

경험 연결 포인트 · 동시 수정, 낙관적 잠금, unique constraint 또는 Redis 원자 연산을 적용했던 사례를 연결합니다.
3

주문 후 10분 안에 결제하지 않으면 재고를 반환해야 합니다. 예약 상태와 만료 작업을 어떻게 설계하고, 중복 실행이나 서버 장애에 어떻게 대응하겠습니까?

답변 예시 보기

진단과 접근

재고 확보와 판매 완료를 하나의 상태로 표현하면 만료 작업과 결제 완료가 충돌합니다. 주문을 RESERVED, PAID, EXPIRED 같은 상태로 관리하고 허용된 상태 전이만 조건부로 수행해야 합니다.

설계와 운영

  • 예약 시 expiresAt을 저장하고 지연 큐나 주기 작업이 만료 후보를 찾습니다.
  • 만료 처리는 WHERE status=RESERVED AND expiresAt<=now 조건으로 EXPIRED 전환에 성공한 경우에만 재고를 반환합니다.
  • 결제 완료도 RESERVED 상태에서만 PAID로 전환하며 같은 주문번호 재호출은 기존 결과를 반환합니다.

지연 큐 하나에만 의존하면 메시지 유실 시 좌석이 남을 수 있으므로 DB의 만료 상태를 다시 훑는 보정 배치를 함께 두는 것이 좋습니다. 만료 지연 건수와 오래된 RESERVED 수를 알림 지표로 둡니다.

경험 연결 포인트 · TTL, 예약 만료, 보상 작업 또는 상태 머신을 운영한 경험과 중복 실행을 막은 방법을 설명합니다.

사내 URL 단축 서비스

상황

메시지와 이메일에 넣을 링크를 줄이는 사내 서비스 ‘ShortLink’를 만듭니다. 링크 생성은 많지 않지만 발송된 메시지를 통한 접속은 하루 수천만 건이며, 특정 이벤트 링크에 트래픽이 집중될 수 있습니다. 이미 발급한 주소가 다른 페이지를 가리키면 큰 사고가 됩니다.[요청] “짧은 주소는 중복되지 않아야 하고, 자주 열리는 링크는 빠르게 응답해야 합니다. 만료된 링크와 운영자가 차단한 링크도 구분해 주세요.”

조건

규모와 시스템 구성

  • 하루 10만 링크 생성, 3천만 리다이렉트
  • 기본 보존 기간 3년
  • 사용자 지정 별칭은 선택 기능

현재 문제와 제약

  • Collision짧은 키 중복 가능성
  • Read Heavy조회가 생성보다 훨씬 많음
  • Expiry만료·차단 상태 처리

꼬리 질문

1

짧은 키를 어떤 방식으로 만들고 중복을 어떻게 막겠습니까? 같은 생성 요청이 재시도될 때 결과가 달라지지 않게 하는 방법도 설명해 주세요.

답변 예시 보기

진단과 접근

단축 키는 유일하고 발급 후 다른 URL로 바뀌지 않아야 합니다. 자동 생성 키와 사용자 별칭의 생성 정책을 먼저 구분하고 DB unique constraint를 최종 방어선으로 둡니다.

설계와 운영

  • DB sequence나 분산 ID를 Base62로 변환하면 충돌 검사가 단순하며, 랜덤 키는 충돌 시 재시도가 필요합니다.
  • 생성 요청에 idempotency key를 받아 응답 유실 후 같은 요청이 와도 기존 키를 반환합니다.
  • 사용자 별칭은 별도 예약 API와 unique index로 중복을 막고 삭제 후 재사용 정책을 명확히 합니다.

예측 가능한 키가 보안상 문제라면 충분히 긴 랜덤 키가 더 적합합니다. 어떤 방식을 택하든 생성 성공 직후 유일성, 재시도, 동시 요청을 테스트해야 합니다.

경험 연결 포인트 · 주문번호, 초대 코드, 멱등키처럼 중복되지 않는 식별자를 만든 경험을 연결합니다.
2

리다이렉트 응답을 빠르게 하기 위해 캐시를 어디에 적용하고, 캐시에 값이 없을 때 어떤 흐름으로 조회하겠습니까?

답변 예시 보기

진단과 접근

리다이렉트는 읽기가 압도적으로 많고 매핑이 거의 변하지 않으므로 cache-aside가 적합합니다. 요청은 애플리케이션 캐시 또는 Redis를 먼저 보고 miss일 때 DB에서 읽어 캐시에 넣습니다.

설계와 운영

  • 인기 링크는 CDN 또는 edge cache까지 올려 애플리케이션에 도달하는 요청을 줄입니다.
  • 동시에 같은 키가 miss되면 한 요청만 DB를 조회하도록 요청 병합을 적용합니다.
  • 없는 키도 짧게 negative cache하여 무작위 키 요청이 DB를 반복 조회하지 않게 합니다.

TTL을 길게 하면 적중률은 좋아지지만 만료·차단 반영이 늦습니다. 매핑과 정책 상태의 TTL을 다르게 두고 cache hit ratio, DB QPS, p99를 측정합니다.

경험 연결 포인트 · Redis, CDN 또는 로컬 캐시의 적중률과 원본 부하를 개선한 경험을 이야기합니다.
3

링크가 만료되거나 악성 링크로 차단됐을 때 오래된 캐시 때문에 계속 열리는 문제를 어떻게 줄이겠습니까?

답변 예시 보기

진단과 접근

링크 목적지와 운영 상태를 분리해 관리하는 편이 좋습니다. 매핑은 긴 TTL로 캐시하더라도 만료·차단 상태는 짧은 TTL 또는 변경 이벤트로 빠르게 갱신합니다.

설계와 운영

  • 차단 변경 시 linkId와 정책 version을 담은 무효화 이벤트를 각 서버와 CDN에 전파합니다.
  • 리다이렉트 시 최신 차단 목록 또는 짧은 정책 캐시를 확인해 오래된 목적지 캐시만으로 열리지 않게 합니다.
  • 전파 실패를 대비해 주기적으로 정책 버전을 비교하고 차단 반영 시간과 실패 노드를 관측합니다.

모든 캐시를 즉시 완벽하게 지우기 어렵기 때문에 보안 차단은 별도 deny-list로 우선 적용하는 전략이 현실적입니다. 오탐 해제와 롤백 절차도 같은 수준으로 준비합니다.

경험 연결 포인트 · 설정·권한·캐시 무효화를 여러 서버에 전파하고 누락을 탐지했던 경험을 연결합니다.

멀티채널 알림 발송 서비스

상황

주문, 배송, 보안 서비스가 문자·이메일·앱 푸시를 각각 직접 발송하고 있습니다. 공급자 장애가 주문 API까지 느리게 만들고 같은 알림이 두 번 발송되는 사례가 발생해 공통 알림 서비스 ‘NotifyOne’으로 통합하려 합니다.[요청] “주문 API는 알림 공급자의 응답을 기다리지 않아야 합니다. 긴급 보안 알림은 마케팅 알림보다 먼저 처리하고, 실패한 알림은 다시 보낼 수 있어야 합니다.”

조건

규모와 시스템 구성

  • 평균 초당 5천 건, 캠페인 시 5만 건
  • 문자·이메일·앱 푸시 3개 채널
  • 발송 결과 30일 보관

현재 문제와 제약

  • Coupling외부 장애가 업무 API에 전파
  • Duplicate재시도 중 중복 발송
  • Priority긴급·일반 알림 경쟁

꼬리 질문

1

알림 요청을 받은 시점부터 외부 공급자에게 발송할 때까지의 비동기 흐름과 주요 컴포넌트를 설명해 주세요.

답변 예시 보기

진단과 접근

업무 API가 외부 공급자를 직접 호출하면 공급자 지연이 주문 처리에 전파됩니다. 요청 접수와 실제 발송을 분리하고, 접수 성공 이후에는 notificationId로 상태를 추적하는 비동기 구조가 적합합니다.

설계와 운영

  • 업무 서비스는 알림 요청을 DB나 메시지 큐에 안전하게 기록하고 즉시 접수 결과를 반환합니다.
  • 채널별 worker가 템플릿과 수신 동의를 검증한 뒤 공급자 adapter를 호출합니다.
  • 상태는 ACCEPTED, SENDING, SENT, FAILED로 저장하고 지연 시간·실패율·큐 적체를 관측합니다.

큐에 넣었다는 것은 사용자에게 전달됐다는 의미가 아닙니다. API 계약에서 접수 성공과 최종 발송 성공을 구분하고, 필요한 업무에는 webhook이나 조회 API를 제공합니다.

경험 연결 포인트 · 외부 API 호출을 비동기로 분리하거나 작업 상태를 조회 가능하게 만든 경험을 설명합니다.
2

외부 문자 공급자가 타임아웃을 반환했지만 실제 발송 여부를 알 수 없을 때 재시도 정책을 어떻게 정하겠습니까?

답변 예시 보기

진단과 접근

타임아웃은 실패가 아니라 결과를 모르는 상태입니다. 무조건 재시도하면 중복 문자가 발생할 수 있으므로 공급자의 idempotency key나 발송 결과 조회 기능을 먼저 확인해야 합니다.

설계와 운영

  • notificationId를 공급자 요청 키로 전달하고 동일 키 재요청 시 중복 발송하지 않도록 합니다.
  • 일시 오류만 지수 백오프로 제한 재시도하고 잘못된 번호 같은 영구 오류는 즉시 실패 처리합니다.
  • 결과 불명 건은 별도 상태로 두고 공급자 조회 API나 운영 확인 후 재처리합니다.

개인화 순위처럼 점수가 자주 바뀌면 cursor 안정성이 더 어려워집니다. 이 중급 사례에서는 시간순이라는 요구를 활용해 계약을 단순화합니다.

경험 연결 포인트 · offset 페이지네이션의 중복·누락을 cursor 방식으로 개선한 경험을 연결합니다.
3

이미 피드 캐시에 들어간 글이 삭제되거나 작성자가 차단됐을 때 어떤 단계에서 필터링하고 정리하겠습니까?

답변 예시 보기

진단과 접근

모든 timeline에서 삭제된 글을 즉시 찾아 제거하면 쓰기 비용이 큽니다. 조회할 때 원본 글 상태와 차단 목록을 최종 확인하고 비동기로 캐시를 정리하는 조합이 안전합니다.

설계와 운영

  • 게시물 삭제 시 tombstone 또는 deleted 상태를 먼저 기록해 원본 조회가 내용을 반환하지 않게 합니다.
  • 삭제 이벤트로 timeline 캐시와 검색 인덱스를 비동기 정리합니다.
  • 차단 목록은 사용자별 짧은 캐시로 조회 경로에서 필터링하고 변경 시 무효화합니다.

조회 시 필터는 정확하지만 비용이 들고 비동기 정리는 빠르지만 지연될 수 있습니다. 둘을 함께 사용하고 삭제 반영 시간과 필터 누락을 측정합니다.

경험 연결 포인트 · 캐시나 검색 인덱스 같은 파생 데이터에서 삭제·권한 변경을 반영한 경험을 설명합니다.

주문 모놀리스의 MSA 분리

상황

10년 된 쇼핑몰 모놀리스에는 주문, 결제, 배송, 쿠폰 코드가 한 애플리케이션과 하나의 DB에 섞여 있습니다. 작은 배송 기능 변경에도 전체를 배포해야 하고, 주문 테이블을 여러 팀이 직접 수정해 장애 원인을 찾기 어렵습니다. 우선 배송 기능부터 독립 서비스로 분리하려 합니다.[요청] “업무 중단 없이 조금씩 분리하고 싶습니다. 서비스를 나누는 것 자체보다 각 팀의 책임과 데이터 변경 권한을 명확하게 해 주세요.”

조건

규모와 시스템 구성

  • 일 주문 100만 건, 피크 초당 500건
  • Java 모놀리스와 MySQL 공유 DB
  • 주문·결제팀과 배송팀이 별도 조직

현재 문제와 제약

  • Boundary서비스 경계 불명확
  • Shared DB여러 서비스의 직접 수정
  • Migration한 번에 전환하기 어려움

꼬리 질문

1

배송 서비스를 어떤 기준으로 분리하고 주문 서비스와 어떤 데이터·API 계약을 맺겠습니까? 테이블 기준 분리의 문제도 설명해 주세요.

답변 예시 보기

진단과 접근

서비스 경계는 테이블 개수보다 업무 책임과 변경 이유로 정해야 합니다. 배송은 운송장, 배송 상태, 택배사 연동을 소유하고 주문은 구매 계약과 주문 상태를 소유하도록 구분할 수 있습니다.

설계와 운영

  • 주문이 배송 생성을 요청할 때 orderId, 배송지 snapshot, 상품 정보를 명시적 API나 이벤트 계약으로 전달합니다.
  • 배송 서비스가 주문 테이블을 직접 수정하지 않고 배송 상태 변경 이벤트를 발행합니다.
  • 계약 version과 소유 팀을 문서화하고 consumer contract test로 변경 영향을 확인합니다.

너무 잘게 나누면 호출과 운영 복잡도가 늘고 너무 크게 두면 독립 배포의 이점이 줄어듭니다. 함께 변경되는 업무와 팀 책임을 기준으로 시작해 실제 변경 패턴으로 조정합니다.

경험 연결 포인트 · 모듈 또는 서비스 책임을 나누고 팀 간 API 계약을 정했던 경험을 이야기합니다.
2

초기에는 배송 서비스가 기존 주문 DB를 읽어야 한다면 어떤 임시 단계를 거쳐 데이터 소유권을 옮기겠습니까?

답변 예시 보기

진단과 접근

초기 공유 DB 접근은 전환을 위한 임시 단계로 사용할 수 있지만 읽기 전용과 종료 시점을 명확히 해야 합니다. 신규 서비스가 계속 기존 테이블을 직접 쓰면 데이터 소유권은 바뀌지 않습니다.

설계와 운영

  • 1단계에서 배송 서비스는 adapter를 통해 기존 조회만 수행하고 모든 신규 배송 코드는 한 경로로 모읍니다.
  • 2단계에서 CDC나 이벤트로 배송 DB에 필요한 read model을 만들고 shadow 비교로 누락을 확인합니다.
  • 3단계에서 배송 쓰기를 신규 DB로 전환하고 기존 테이블에는 호환용 결과만 동기화한 뒤 의존을 제거합니다.

이중 쓰기는 한쪽만 성공할 수 있으므로 오래 유지하지 않습니다. 각 단계마다 단일 writer를 정하고 데이터 건수·상태별 대사와 rollback 조건을 둡니다.

경험 연결 포인트 · 공유 DB 의존을 줄이거나 읽기 모델을 분리한 경험과 임시 구조를 언제 제거했는지 설명합니다.
3

기존 경로와 신규 배송 서비스를 함께 운영하면서 트래픽을 점진적으로 전환하고 문제가 생기면 어떻게 되돌리겠습니까?

답변 예시 보기

진단과 접근

Gateway 또는 기존 모놀리스 내부 라우터에서 사용자나 주문 ID를 기준으로 안정적으로 신규 경로를 선택하면 같은 요청이 경로를 오가는 문제를 줄일 수 있습니다.

설계와 운영

  • 사내 사용자와 테스트 주문부터 시작해 1%, 5%, 20% 순으로 확대합니다.
  • 구·신 경로 응답과 상태 변화를 shadow 비교하고 오류율, 지연, 배송 생성 성공률을 확인합니다.
  • 신규 경로를 끄는 feature flag와 DB 호환성을 유지해 수 분 안에 기존 경로로 돌아갈 수 있게 합니다.

쓰기 요청을 구·신 시스템에 동시에 실행하면 중복 배송이 생길 수 있으므로 shadow는 읽기 또는 부작용 없는 검증에만 사용합니다. 단일 writer 원칙을 유지합니다.

경험 연결 포인트 · 카나리 배포, feature flag 또는 점진 트래픽 전환과 rollback 경험을 수치로 설명합니다.

MSA 동기 호출 연쇄 장애

상황

상품 상세 API가 회원, 가격, 재고, 추천 서비스를 HTTP로 순서대로 호출합니다. 추천 서비스 응답이 느려진 날 상품 API의 스레드가 모두 대기하면서 관련 없는 상품 조회까지 실패했습니다. 각 팀은 자신의 서비스만 정상이라고 판단해 원인 파악에도 시간이 오래 걸렸습니다.[요청] “부가 기능 하나가 느려져도 핵심 상품 정보는 보여야 합니다. 어느 서비스에서 시간이 걸렸는지 한 요청 흐름으로 추적할 수 있어야 합니다.”

조건

규모와 시스템 구성

  • 상품 조회 초당 1만 건
  • 내부 서비스 호출 4~7회
  • 응답 목표 p95 300ms

현재 문제와 제약

  • Cascade느린 호출이 전체 장애로 확대
  • Timeout서비스마다 제각각인 제한 시간
  • Tracing요청 흐름 추적 어려움

꼬리 질문

1

전체 응답 시간 300ms 안에서 각 내부 호출의 timeout을 어떻게 정하고 필수·선택 데이터를 어떻게 구분하겠습니까?

답변 예시 보기

진단과 접근

전체 300ms를 각 호출에 그대로 주면 마지막 단계에서 시간 예산이 사라집니다. 호출의 중요도와 예상 지연을 기준으로 전체 deadline을 나누고 선택 기능은 더 짧게 제한합니다.

설계와 운영

  • 상품·가격·재고를 필수 데이터로, 추천을 선택 데이터로 분류합니다.
  • 병렬 호출 가능한 서비스는 동시에 요청하고 전체 deadline의 남은 시간을 downstream에 전달합니다.
  • 서비스별 p95와 오류율을 보고 timeout을 조정하며 timeout 횟수와 전체 응답 시간의 관계를 관측합니다.

timeout이 너무 짧으면 정상 요청도 실패하고 너무 길면 스레드가 고갈됩니다. 평균값이 아니라 tail latency와 사용자 허용 시간을 기준으로 설정합니다.

경험 연결 포인트 · 외부 또는 내부 API timeout을 정하고 실제 지연 분포로 조정한 경험을 설명합니다.
2

추천 서비스 장애 시 timeout, circuit breaker, fallback을 어떤 순서로 적용하고 사용자에게 어떤 결과를 보여주겠습니까?

답변 예시 보기

진단과 접근

추천은 선택 데이터이므로 장애 시 핵심 상품 조회를 실패시키지 않는 것이 우선입니다. 짧은 timeout 후 circuit breaker가 열리면 즉시 fallback을 반환합니다.

설계와 운영

  • 일정 실패율 이상이면 회로를 열고 추천 호출을 잠시 중단해 느린 서비스와 호출자의 자원을 함께 보호합니다.
  • fallback은 빈 추천, 최근 인기 상품, 캐시된 결과 중 제품 요구에 맞게 선택합니다.
  • half-open 상태에서 소량 요청으로 복구를 확인하고 자동으로 정상 호출을 재개합니다.

모든 오류에 동일 정책을 적용하지 않습니다. 잘못된 인증처럼 재시도로 회복되지 않는 오류는 즉시 실패시키고 일시 장애만 제한적으로 재시도합니다.

경험 연결 포인트 · circuit breaker나 fallback으로 부가 기능 장애를 격리한 경험과 사용자 영향을 이야기합니다.
3

분산 로그, metric, trace에 어떤 공통 식별자와 정보를 남겨 연쇄 장애의 시작점을 찾겠습니까?

답변 예시 보기

진단과 접근

한 요청에 공통 traceId를 부여하고 서비스가 다른 서비스를 호출할 때 전달해야 전체 흐름을 연결할 수 있습니다. 로그, metric, trace가 같은 서비스명과 오류 분류를 사용해야 분석이 쉬워집니다.

설계와 운영

  • 각 span에 서비스명, API, 소요 시간, 상태 코드, timeout 여부와 downstream 이름을 기록합니다.
  • 개인정보나 전체 요청 본문은 남기지 않고 orderId 같은 업무 키도 정책에 맞게 마스킹합니다.
  • 전체 p95뿐 아니라 downstream별 지연, circuit 상태, timeout 비율을 대시보드로 묶습니다.

모든 요청을 100% 상세 추적하면 비용이 크므로 오류 요청과 느린 요청을 우선 보존하고 정상 요청은 샘플링할 수 있습니다.

경험 연결 포인트 · correlation ID, 분산 trace 또는 공통 로그 포맷으로 장애 분석 시간을 줄인 경험을 설명합니다.

레거시 주문 조회 API 분리

상황

레거시 쇼핑몰의 주문 조회는 여러 Stored Procedure와 15개 테이블을 조인해 평균 3초가 걸립니다. 모바일 앱은 오래된 응답 형식에 강하게 의존하고 있어 한 번에 API를 바꾸기 어렵습니다. 신규 조회 서버를 만들고 일부 사용자부터 전환하려 합니다.[요청] “앱을 수정하지 않고 조회 성능을 개선하며, 신규 서버에 문제가 생기면 즉시 기존 경로로 돌아갈 수 있어야 합니다.”

조건

규모와 시스템 구성

  • 주문 이력 5년, 30억 행
  • Oracle 기반 모놀리스
  • 조회 API p95 3초 → 목표 500ms

현재 문제와 제약

  • Contract기존 응답 형식 유지
  • Read Load운영 DB 조회 부하
  • Rollback신규 경로 장애 시 복귀

꼬리 질문

1

API Gateway나 BFF를 이용해 기존 클라이언트 요청을 신규 조회 서버로 점진 전환하는 방법을 설명해 주세요.

답변 예시 보기

진단과 접근

클라이언트 계약은 유지하고 Gateway가 같은 URL을 구·신 서버 중 하나로 라우팅하게 하면 앱 변경 없이 전환할 수 있습니다. 사용자 ID 해시로 경로를 고정하면 비교와 문제 재현이 쉽습니다.

설계와 운영

  • 사내 계정부터 신규 서버로 보내고 오류율과 p95를 확인한 뒤 비율을 단계적으로 높입니다.
  • 신규 서버 장애 시 route weight를 0으로 만드는 빠른 rollback 절차를 준비합니다.
  • 인증, rate limit은 Gateway 공통 정책으로 두고 복잡한 업무 변환은 신규 서비스 adapter가 담당합니다.

무작위 요청 단위 분배는 한 사용자가 매번 다른 결과를 볼 수 있습니다. sticky routing을 사용하고 전환 비율별 관찰 시간을 정합니다.

경험 연결 포인트 · API Gateway, reverse proxy 또는 feature flag로 트래픽을 점진 전환한 경험을 연결합니다.

여러 팀이 각자 서버 로그와 metric을 관리해 장애 발생 시 공통 원인을 찾기 어렵습니다. 간단한 통합 모니터링을 구축하려 하지만 한 서비스가 너무 많은 로그를 보내면 수집 서버와 저장소가 느려집니다.[요청] “모니터링 장애가 실제 서비스 요청을 느리게 만들면 안 됩니다. 중요한 오류는 빠르게 찾고, 오래된 데이터는 저렴하게 보관해 주세요.”

조건

규모와 시스템 구성

  • 서비스 300개, 초당 로그 20만 건
  • metric 10초 주기 수집
  • 최근 7일 빠른 조회, 90일 보관

현재 문제와 제약

  • Backpressure수집 지연이 서비스로 전파
  • Volume특정 서비스 로그 폭증
  • Alert같은 장애의 중복 알림

꼬리 질문

1

애플리케이션에서 로그·metric을 수집하고 중앙 저장소에 적재하는 흐름을 비동기로 구성해 주세요.

진단과 접근

애플리케이션은 로그 전송 완료를 기다리지 않고 로컬 agent나 비차단 버퍼에 기록해야 합니다. 중앙 collector가 이벤트를 받아 queue에 저장하고 저장·색인 작업자가 비동기로 처리합니다.

설계와 운영

  • 애플리케이션→로컬 agent→collector→durable queue→검색/metric 저장소로 단계를 분리합니다.
  • 공통 필드로 timestamp, service, environment, level, traceId를 정의합니다.
  • 수집 지연, queue age, 저장 실패, 서비스별 유입량을 관측해 어느 구간이 막혔는지 확인합니다.

모니터링 데이터의 완전성을 높이려다 서비스 요청이 느려져서는 안 됩니다. 감사 로그처럼 반드시 보존할 데이터는 일반 디버그 로그와 별도 경로로 구분합니다.

경험 연결 포인트 · 로그나 이벤트 수집을 비동기로 분리해 본 서비스의 지연을 보호한 경험을 연결합니다.
2

수집 서버나 저장소가 느려질 때 애플리케이션을 보호하기 위한 로컬 버퍼, 샘플링, 폐기 우선순위를 어떻게 정하겠습니까?

진단과 접근

중앙 수집이 느릴 때 로컬 버퍼에는 상한이 있어야 하며 중요도에 따라 무엇을 버릴지 미리 정해야 합니다.

설계와 운영

  • ERROR와 핵심 업무 metric은 우선 보존하고 DEBUG·반복 로그는 먼저 샘플링하거나 폐기합니다.
  • 버퍼가 가득 차도 애플리케이션 스레드를 오래 막지 않고 손실 건수를 별도 metric으로 남깁니다.
  • 서비스별 전송 quota와 rate limit으로 한 팀의 폭주가 전체 수집기를 고갈시키지 않게 합니다.

디스크 버퍼는 장애 시간을 견디지만 디스크 고갈 위험이 있습니다. 최대 용량과 보존 시간을 정하고 오래된 낮은 우선순위 데이터부터 삭제합니다.

경험 연결 포인트 · backpressure 상황에서 버퍼 상한과 drop policy를 정하고 데이터 손실을 가시화한 경험을 설명합니다.

한 장애로 같은 알림이 계속 발생하지 않도록 알림 조건, 묶음, 재알림 간격을 어떻게 설정하겠습니까?

답변 예시 보기

진단과 접근

알림은 순간 한 번의 임계치 초과보다 일정 시간 지속되는 사용자 영향에 초점을 두어야 합니다. 같은 원인의 알림은 서비스와 오류 유형 기준으로 묶습니다.

설계와 운영

  • 5분 중 3회 이상 임계치 초과처럼 지속 조건을 두고 정상 복귀에도 여유 구간을 둡니다.
  • 같은 서비스·원인의 알림은 하나의 incident로 group하고 일정 시간 동안 중복 통지를 억제합니다.
  • 심각도에 따라 즉시 전화, 메신저, 업무 시간 알림을 구분하고 ACK가 없을 때만 다음 담당자에게 전달합니다.

알림을 줄이는 과정에서 실제 장애 탐지가 늦어지지 않도록 알림 수, 오탐률, 탐지 시간, ACK 시간을 함께 측정합니다.

경험 연결 포인트 · 반복 알림이나 오탐을 줄이면서 중요한 장애 탐지를 유지한 경험을 수치와 함께 설명합니다.
